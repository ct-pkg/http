# PH-12 开卡 battle · 反方（S-01 响应头读取 + S-02 `method()`）

- 命题：现在开 PH-12，交付 S-01（响应头读取）与 S-02（`method()`）。
- 立场：反方。
- 结论：**NO-GO（现在不开）**。

不是因为这两项永远不该做，而是因为现在开卡会把「需求层未裁定」直接压成「实现层已冻结」：
S-02 全仓找不到需求方；S-01 的真实成本已被规格评审拆成 5 个未决契约问题，不是 PH-4 卡里那个
「1 个 S 任务」；而一个相要为此付出 `0.3.0` + 新 tag 推送 + 全套文档对账。建议先把需求层裁定做完
（纯文档，不占相、不 bump、不打 tag），实现等有真实消费者判据再开。

本文只做判断，不改实现、不改 `ct.pkg`、不提交。

## 1. 硬伤

### 1.1 顺序错：先开卡等于先冻结没有合法来源的判据

G1 要求每条要求有 ID、每条验收判据有命令与阈值；G2 要求每条 `R-*` 映射到可跑的 `ACC-*`
（`AGENTS.md:49-50`；`docs/acceptance-map.md:5-7`）。现在：

- R-04 明文写「不提供响应头读取」（`docs/requirements.md:73`）；
- R-11 明文写「不读响应头」，且读取面判据只列 6 项（`:146-149`）；
- R-10 明文写「不提供 GET/PUT/DELETE 或自定义 method」（`:139`）。

在这个状态下写 PH-12 卡，只有两种结果：

1. 卡片的退出判据与冻结需求正面相反 → G1/G2 无法自洽；
2. 先改写 R-04/R-10/R-11 再开卡 → 那是**需求层裁定**（要用户签字），不是 phase 任务。

features 文档已经写死顺序：「未裁定的项不进入 phase 1；其余 phase 的卡片必须写明『按裁定结果执行』」
（`docs/planning/ct-http-0.1.0-features.md:60`）。现在开卡是跳过了这一步，把「待裁定」当成「已裁定」。

**这是本文最强的一条：不是能力不够，是判据来源不合法。**

### 1.2 S-01 的成本被低估：不是「1 个 S 任务」

PH-4 卡当时登记的是「待裁定，实现成本 S（约 1 个任务：header 回调 + 存储 + 查询）」
（`docs/phases/PH-4/card.md:48`、`:133`）。但同一仓库的规格评审已经把响应头读取拆成 5 个未决契约问题：

| 编号 | 问题 | 为什么不是实现细节 |
| --- | --- | --- |
| B-4 | 302 的中间响应头与 200 的最终响应头混在同一查询面 | 查哪个由实现自定，下游会把 `text/html` 误判成 `text/event-stream`（`spec-rebuttal.md:129-137`） |
| B-6 | 头名大小写未归一 | `content-type` 与 `Content-Type` 两种实现都「符合」现有文字（`:149-157`） |
| B-7 | `header_all` 的生命周期、顺序、重复项、原型未冻结 | 两个 `Set-Cookie` 返回什么无法唯一推出（`:159-167`） |
| B-8 | 响应头没有上限，`max_body_bytes` 管不到 | 10 万个头可在解码阶段耗尽内存（`:169-177`） |
| F-3 | 与 R-04/R-11 非目标正面冲突 | 加 `header_all` 会直接打破 R-11 的「公开面 6 项」核对（`spec-rebuttal-part2.md:82-90`） |

这五项都是 API 契约决策，不是「回调 + 存储 + 查询」能顺手覆盖的。拿 PH-4 的 S 估算给 PH-12 定价，
是在用一个已被本仓评审推翻的旧数字做预算。

### 1.3 S-02：没有需求方，且两条分支都不便宜

先说需求侧：我在同级仓里找不到任何一个包要求 GET / HEAD / 自定义 method。

- `ct-llm-sse/docs/requirements.md` 的输入是「状态码 + content-type + 逐块字节」（`:28`、`:41`），
  全篇没有 GET/方法需求；
- `ct-sse`、`ct-json` 等同类仓也没有；
- 唯一提到「方法」的是 ct-http 自己的 S-02 条目。

也就是说，S-02 目前是「提案里想要」，不是「下游要」。

再说实现侧，S-02 有两条互斥分支，各自代价不同：

| 分支 | 后果 | 成本 |
| --- | --- | --- |
| 替换：`.post()` 改为 `.method()` | 对**已发布**的 0.2.0 是破坏性变更；6.7 规定 MAJOR 需用户裁定，且 MAJOR 会打乱 `MINOR == n - d` 的相位映射 | 全仓 36 个文件、44 处 `.post(`/`->post(` 需改；README、教程、夹具、golden 全动 |
| 新增：保留 `.post()`，另加 `.method()` | 非破坏，但两个入口做同一件事，优先级未定义；features 文档明确要求「如果同时保留 `.post()`，要定义二者优先级」（`features.md:74`） | 虽小，但换来一个重复入口 + 一条必须长期维护的歧义规则 |

roadmap 已选了新增路线（`docs/planning/ct-http-0.1.0-roadmap.md:40`：「新增 `.method("GET")` 入口，
不改已冻结的方法名」）。那命题必须承认：S-02 只是**增加一个当前无人使用的第二入口**。

### 1.4 收益不支撑一个相

一个 phase 不是一次提交，是一整套：新会话、新卡、基线、≥3 条带命令锚点的退出判据、
逐任务红绿证据、g0–g9、版本移动、`applies-to` 全量同步、CHANGELOG、acceptance-map、
annotated tag + 推送（`docs/session-map.md:30`；`PH-11/card.md:62-96`；`AGENTS.md:121`）。

而现在的收益面是：

- S-01：唯一具名受益方是 `ct-llm-sse`（`features.md:66`），但该包目前**只有需求文档，没有实现**
  （仓库内只有 `docs/`、`ct.pkg`、`AGENTS.md`、`README.md`），且它对「缺 content-type」还留了
  不依赖响应头的兜底口径（`ct-llm-sse/docs/requirements.md:83`、`:175`，Q-07 口径 A：首字节 `{` 判 JSON）。
  需求在纸面上存在，但既不阻塞任何在跑实现，也尚未冻结。
- S-02：没有需求方（见 1.3），只有提案。

两个独立、未冻结、无活跃消费者的非目标翻转，拼成一个相，本质上是**为了开相而凑内容**。
它们之间也没有依赖关系（读面 vs 写动词），没有理由必须同相。

### 1.5 版本轴容得下 PH-12，但这恰恰意味着逃不掉一次 MINOR 发布与 tag 推送

这一条我给出与「版本对不上所以不能开」相反的结论，避免用假 blocker：**版本映射容得下 PH-12**。
详见 §2。真正的问题不是「放不进」，而是「放进去就得按完整发版走」：

- V-2 规定 PATCH 只记 fix，功能不得占用 PATCH（`AGENTS.md:116`）→ 没有「不占相、不涨 MINOR」的合规落法；
- V-7 规定相收口要建 annotated tag 并推（`AGENTS.md:121`）→ 开相即承诺一次新的对外 tag 推送；
- 收口前 `v0.2.0` 不指向 HEAD，`g8-tag` 必然红（`tools/gates/g8.sh:154-160`），收口时必须落 `v0.3.0`。

为一个无消费者的方法 + 一个契约未定的读面，付出一次 semver 可见的发布与推送，不成比例。

### 1.6 对账面与并发面

开相要动 `AGENTS.md`（deviation V-001 的「现状」行仍是 0.2.0）、`README.md:7`、`:12`、
19 个用户面 `applies-to`、`CHANGELOG.md:6`、`docs/acceptance-map.md`，还要新增 roadmap 段与卡。
当前仓库另有会话在跑、且工作树已有未跟踪文件（`docs/review/*`）。这些共享文档正是最容易撞 index
的地方；先做需求层裁定可以把这批改动推迟到独占总线时再落。

## 2. 版本号 / phase 映射核对（V-1、d=9、门禁实际实现）

结论先行：**PH-12 → `0.3.0` 机械上成立，不需要改任何版本规则。** 成本在收口动作与对账，不在规则。

| 检查 | 实际实现 | PH-12 落点 |
| --- | --- | --- |
| V-1 偏移换算 | `want_minor = MINOR + d`，要求 `docs/phases/PH-<want>/card.md` 存在（`tools/gates/g4.sh:316-326`；`tools/gates/g8.sh:105-113`） | `d = 9`，故 `MINOR = 12 - 9 = 3` → `0.3.0` |
| 卡片字段 | `g1-version` 要求 `- version-minor：<n>` 等于 PH 号（`tools/check.sh:83-87`） | 卡头写 `version-minor：12`（不是 3，3 是产品版本） |
| 版本落点 | `ct.pkg#version`、README 版本行、CHANGELOG 首条三者相等（`tools/gates/g4.sh:307-314`） | 三处同为 `0.3.0` |
| 标签 | annotated `v<version>` 必须指向 HEAD，否则红（`tools/gates/g8.sh:147-160`） | 收口建并推 `v0.3.0` |
| 偏离登记 | `d = 9` 写死为「永久偏移，不设对齐」（`AGENTS.md:284-291`） | 无需改规则；但「现状: 0.2.0」一行会过期，需同步 |
| PATCH 记账 | `d != 0` 时 PATCH 记账延后（`tools/gates/g4.sh:328-334`） | 本相不涉及 |

补充两点，避免被误读：

1. **偏移是永久的**，不存在「某相追平版本号」的选项，所以 PH-12 不会触发重编号，也不会造出空 CHANGELOG 段。
2. 如果 S-02 走**替换**分支，才会真正撞上版本规则：已发布包改公开入口属破坏性变更，
   要 `MAJOR` 由用户裁定，而 `MAJOR` 与 `MINOR == n - d` 的相位映射不兼容。这条只对替换分支成立。

## 3. 替代方案及其代价

| 方案 | 做什么 | 代价 | 评价 |
| --- | --- | --- | --- |
| **A（推荐）只做需求层裁定** | 用一份 proposals/裁定文档把 S-01/S-02 的取舍、契约（B-4/B-6/B-7/B-8）、是否翻非目标写死，用户签字 | 纯文档；不占相、不 bump、不打 tag（V-4：纯文档不 +PATCH） | 成本最小，且解开 1.1 的判据来源问题；不产出实现 |
| **B 延后到有真实消费者** | 等 `ct-llm-sse` 进入实现、其 Q-07 冻结后，用它的 C1/R-A-04 当判据开相 | 延期；但当前没有活跃消费者被阻塞 | 最符合「判据来自需求」；对 S-02 建议直接不做，除非出现 GET 需求 |
| **C 窄接口替代完整读面** | 若只缺 content-type，只加一个 `content_type()`（`CURLINFO_CONTENT_TYPE`），不做 `header()/header_all()` | 仍要改 R-11 非目标 + 一个相；但绕开 B-4/B-6/B-7/B-8 的四个契约决策 | 若一定要现在动，这是成本最低的版本；仍不建议与 S-02 捆绑 |
| **D 并入将来的 0.3.0 相** | 与另一个有真实需求的功能同相，摊销相仪式成本 | 与 A/B 相同的前置；相本身需重新规划 | 可接受，但前提仍是先裁定 |
| **E 现在开 PH-12（命题）** | S-01 + S-02 一个相交付 | 0.3.0 + `v0.3.0` 推送 + 全套对账 + 新会话；S-01 五个契约未决；S-02 无消费者 | 不成比例，且判据来源不合法 |

关于「更便宜的落法」的一句实话：按 6.7 的版本纪律，**功能不能走 PATCH（V-2）**，
所以「不占相的小改动」在这个项目里不是合规选项。能真正省成本的只有「先不实现」或「窄接口」。

## 4. 什么条件下才值得开

满足以下全部条件，我才撤回反方：

1. **需求层已完成**：R-04/R-10/R-11 的非目标被正式改写（用户签字），`docs/acceptance-map.md` 补上新 `ACC-*`，G2 能自洽。
2. **S-01 契约已冻结**：明确「只看最终响应」、大小写不敏感查找、`header_all` 的返回类型/顺序/重复项、头上限与超限错误码（即 B-4/B-6/B-7/B-8 各有结论），并有一条全小写响应的负例。
3. **S-02 有真实需求**：至少一个下游给出 GET/HEAD 的验收判据；且选定「新增」而非「替换」，并写死 `.post()` 与 `.method()` 的优先级。
4. **范围不捆绑**：S-01 与 S-02 若无共同需求，分开评估；不要为了凑一个相把两项无关翻转绑在一起。
5. **版本与轨道明确**：按 `0.3.0`（MINOR=3，d=9）走，新增 0.3.0 roadmap 段与新会话，不接受「0.2.1 塞功能」或「卡先开、需求后补」。
6. **若只缺 content-type**：优先方案 C 的窄接口，而不是完整 `header()/header_all()`。

---

## 5. 反方不主张什么

- 不主张 S-01/S-02 永远不该做；S-01 对 SSE/LLM 下游有真实价值。
- 不主张用 PATCH 偷跑功能（V-2 不允许），也不主张改判据、改 golden、改版本号凑绿。
- 不主张「版本对不上所以不能开」——版本轴是通的，问题在顺序、成本与需求缺位。
- 不主张 S-02 的技术实现有 CT 阻塞；技术可行，缺的是需求与入口语义。
