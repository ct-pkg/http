# S-04 主张席：跨线程取消应纳入 0.1.0（方向 B）

- 日期：2026-11-15
- 议题：`cancel()` 是否允许从另一线程调用
- 主张：纳入，F-11 走方向 B（引用计数 / 取消 token + TSAN）
- 结论状态：**未被采纳**；裁决见 [S-04-ruling.md](S-04-ruling.md)

## 1. 主张

HTTP 客户端最常见的取消场景就是「用户在别的线程点了取消」：UI 线程、信号处理线程、
调度器。如果 `cancel()` 只能在 chunk / 进度回调内调用，调用方已经知道传输正在进行，
却还必须等到下一片数据到达才能停。对「服务器很慢、迟迟不发数据」的请求，回调内取消
没有触发点，等于不可用。

因此 0.1.0 应当：

- 把取消标志做成 `atomic int`，允许任意线程写；
- 增加 `HttpCancel *` 或 `http_request_ref/unref`，让 `cancel()` 调用方与 `send()`
  调用方各自持有一份生命周期，避免「cancel 正在读、send 已 free」的 UAF；
- 用 pthread 夹具 + TSAN 证明并发读写无数据竞争；
- 改写 R-13 的非目标与 Q-12 的线程口径。

## 2. 论据

1. **需求真实**：R-13 的问题陈述是「慢请求要能主动中止」。同线程回调内触发只覆盖了
   「正在收数据」这一种慢；对「连上后首字节迟迟不来」的慢请求无解。
2. **代价可控**：一个 `atomic int` 在 C11 里只是 `_Atomic int` 或 `__atomic_*`，
   现有 `XferState` 只需多存一个指针。
3. **可验证**：TSAN 能在 CI 上跑；pthread 夹具已在 `test/fixtures` 的 C 侧，不引入新依赖。
4. **避免二次改公共面**：0.1.0 若不纳入，0.2.0 加跨线程取消必然要动 `HttpRequest`
   布局与释放契约，届时已发布的调用方要重编译、重审所有权。

## 3. 若采纳，判据会长什么样

- `p8-cancel-cross`：主线程 `send()` 阻塞在慢响应，另一线程 50 ms 后 `cancel()`；
  `send()` 在 3 秒内返回 42、`is_cancelled()==1`。
- `p8-cancel-race`：TSAN 下 cancel 与 free 交错 1000 次，0 报告。
- `p8-refcount`：`unref` 后不释放仍在传输的对象；最后一次 `unref` 才 cleanup。

## 4. 主张席自认的弱点

- 「UI 线程取消」不是本仓的消费者：仓内只有 `ct-llm-sse` 这类同步调用方，没有线程封装。
- TSAN 与 pthread 夹具会把 phase 8 从 S/M 推成 L，且需要新增 CT 之外的构建矩阵。
- 取消语义一旦跨线程，释放语义也必须跨线程；这不是「多一个 atomic」的成本。
