# S-04 裁决：0.1.0 只做同线程取消（方向 A）

- 日期：2026-11-15
- 议题：`cancel()` 是否允许从另一线程调用
- 输入：[主张席](S-04-advocate.md)（纳入，方向 B）、[反证席](S-04-rebuttal.md)（不纳入，方向 A）
- 裁决人：DEV（按 2026-11-15 用户授权「实现细节自行裁定，不回来提问」）
- 裁决：**不纳入跨线程取消；0.1.0 固定为同线程取消（方向 A）**

## 1. 理由

1. R-13、R-02 的非目标与 Q-12 的线程口径都把跨线程排除在 0.1.0 之外；纳入要先改三条
   规范条款并重排 phase 2，收益与成本不匹配。
2. 单一个 atomic 标志不解决生命周期：`cancel()` 线程与 `send()` 线程的 free 竞争是 UAF，
   不是数据竞争。方向 B 的真实成本是取消 token / 引用计数 + TSAN + 并发构建矩阵。
3. CT 标准库无线程封装，跨线程判据只能是 C 夹具，无法证明 CT 调用点。
4. 现有触发点（分片写回调 + 约 1 秒一次的进度回调）已覆盖「慢而持续」与「连上后停顿」；
   「首字节前完全不发数据」属于超时语义，由 `timeout` / `idle_timeout` 负责。

反证席第 2 节承认的两条代价，本裁决用卡片条款与用例正面处理，不留给口头约定。

## 2. 落地的取消语义（写死）

- 入口：`void http_request_cancel(struct HttpRequest *r)`；CT 侧 `req->cancel()`。
  `r == NULL` 是 no-op。**只允许与 `send()` 同线程调用**；跨线程调用是未定义行为，
  README 与头文件注释都写明。
- 标志是**粘性**的：置位后该请求不再发起新的传输。要重试请在新的请求对象上重来。
- 判定点三处，任一命中即中止：
  1. 传输开始前（本地校验与模式锁之后）：不连接、不读服务器，直接 `42`；
  2. 每次写回调交付字节之前：先看标志，命中则中止，这一片不交付；
  3. 每次进度回调（约 1 秒一次）：命中则中止。
- 对外形态：`error()==42`（`CURLE_ABORTED_BY_CALLBACK`）、`is_cancelled()==1`、
  `is_ok()==0`、`timeout_kind()==0`。
- 优先级（同一时点只判一个）：取消 `42/cancelled=1` > 回调中止 `23/cancelled=0` >
  上限 `-1008` > 空闲 `28/3` > 传输码。写回调在调用用户回调之前先查取消标志，
  所以用户回调同时「取消 + 返回非 0」时按取消记账。
- 精度：连续有数据的流在下一次写回调即停（毫秒级）；无数据的停顿流要等下一次进度回调，
  约 1 秒。**DNS 解析阶段不可取消**：解析返回前不会观察到标志，解析返回后由上述判定点接手。
- 已收数据的归属：非流式保留已收前缀，`body_len()==total_bytes()`，`take_body()` 可取；
  流式已交付片归调用方，`body()==NULL`、`body_len()==0`、`take_body()==NULL`。
- 成功路径：`is_cancelled()==0`、`error()==0`。

## 3. 规范影响

**不改 `docs/requirements.md` 与 `docs/design.md`。** R-13 已经定义了
`cancel()` / `is_cancelled()` 与「同线程、回调内」的 0.1.0 口径，本次裁决落在该口径内，
没有新增或改写条款；S-04 在 roadmap 与 feature 表中继续记为「不进入 0.1.0」。

## 4. 重新裁定的触发条件

- 出现真实消费者需要「另一线程中止正在进行的请求」；
- 0.2.0 排期启动，且连接池 / multi 进入范围。

届时按方向 B 立项：取消 token 或 `http_request_ref/unref` + pthread 夹具 + TSAN，
并先改写 R-13、R-02、Q-12。
