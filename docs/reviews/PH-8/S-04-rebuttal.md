# S-04 反证席：0.1.0 不做跨线程取消（方向 A）

- 日期：2026-11-15
- 议题：`cancel()` 是否允许从另一线程调用
- 主张：不纳入；F-11 走方向 A（同线程取消 + 显式释放）
- 结论状态：**已采纳**；裁决见 [S-04-ruling.md](S-04-ruling.md)

## 1. 反证

### 1.1 规范已经把它列成非目标

R-13 非目标原文：「不支持跨线程取消、异步取消、信号触发」；R-02 非目标：「不做跨线程
共享句柄」；Q-12「线程安全口径」未定。S-04 若要纳入，必须先改写三条规范条款，再重排
phase 2 的生命周期与 phase 8 的取消。0.1.0 的冻结面里没有任何一条要求跨线程。

### 1.2 单一个 atomic 不足以让 cancel 安全

主张席的最小方案（`atomic int` 标志）只解决「读写不撕裂」，不解决生命周期：

- `cancel()` 线程读到 `r->cancel_requested` 之前，`send()` 线程可能已经
  `http_request_free(&r)`，这是 use-after-free，不是数据竞争；
- 要让 cancel 安全，必须引入取消 token 或引用计数，把「请求对象」与「easy handle」
  的寿命拆开；目录里现有 3 个释放入口（`http_request_free` / `_release` /
  `request_destroy`）都要重写，且 `take_body` 的所有权表要重审。

这已经是方向 B 的完整成本，远超「加一个 atomic」。

### 1.3 判据无法在纯 CT 内落地

CT 标准库没有线程封装。跨线程夹具只能是 C 夹具，`p8-cancel-cross` 无法证明 CT 调用点
可用；TSAN 还要新增一条构建矩阵（macOS 的 TSAN + libcurl 系统库有已知噪声）。
本仓的门禁是 `bash tools/check.sh g3` 一条命令跑完；引入并发矩阵会把它拆成两套，
且 flaky 风险上升。

### 1.4 现有触发点已覆盖「慢」的主要形态

`send_stream` 的回调每收到一片就执行一次，配合进度回调（约 1 秒一次），
「慢而持续」和「连上后停顿」两种慢都能在 ≤1 个回调周期内被取消。
唯一未覆盖的是「首字节前完全不发数据」——那种场景由 `timeout` / `idle_timeout`
负责，本来就是超时语义，不是取消语义。

### 1.5 消费者不存在

本仓的调用方是同步的；0.1.0 没有连接池、没有 multi。为一个不存在的调用方引入线程设施，
违反「只做最短路径」的定位（README「定位与边界」）。

## 2. 反证席承认的代价

- 0.2.0 若加跨线程取消，会动 `HttpRequest` 布局与释放契约，属于源码级破坏；
  必须在 README 写明「同线程」限制，避免调用方误用。
- 回调外、连接前的取消需要显式语义，否则调用方会以为「cancel 了就会立刻停」。
  这个语义必须在卡里写死并有用例，不能靠口头约定。
